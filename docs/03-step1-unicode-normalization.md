# 03. 1단계 — Unicode Normalization

## 목적

유니코드에는 같은 글자를 표현하는 여러 방법이 존재한다 (전각/반각, 합성 문자 vs 결합 문자, 호환 문자 등). 이를 표준 형식으로 수렴시켜 이후 단계(특히 문자열 매칭 기반 탐지)가 "같은 것을 같다고" 볼 수 있게 한다.

## 정책

- 기본 정규화 형식: **NFKC** (Compatibility Composition)
  - 전각 영숫자(`Ａ`→`A`, `１`→`1`), 반각 카타카나(`ｶﾀｶﾅ`→`カタカナ`), 로마숫자/원문자(`Ⅳ`→`IV`) 등 호환 문자를 표준 형태로 접는다. 보안 우회 탐지 관점에서 NFKC가 NFC보다 유리한 이유는, 공격자가 전각/호환 문자를 이용해 금칙어 문자열 매칭을 우회하는 가장 흔한 수법을 이 단계에서 대부분 무력화하기 때문.
  - 트레이드오프: NFKC는 일부 의미 구분을 잃는다 (예: 위첨자 숫자와 일반 숫자가 같아짐). 이 라이브러리의 목적(정규화된 탐지 뷰)에서는 허용 가능한 손실로 판단.
- `NormalizationConfig.unicode.form`으로 `NFC`/`NFD`/`NFKC`/`NFKD` 선택 가능 (기본값 `NFKC`).
- 정규화 전/후 텍스트가 다르면 `Transformation(step="unicode", rule=f"normalize_{form}")` 기록. 개별 문자 단위가 아니라 변경된 구간 단위로 묶어서 기록한다 (전체를 한 덩어리로 기록하면 span이 너무 커지므로, 연속으로 변경되지 않은 구간을 기준으로 diff).

## 플래그

- NFKC 적용 후 길이가 유의미하게 줄어드는 호환 문자 치환이 많이 발생하면(예: 원문의 30% 이상이 풀와이드/호환 문자) `SuspicionFlag(category="mixed_script"...)`가 아니라 별도 경량 신호로 `metadata`에만 남기고 별도 플래그는 만들지 않는다 (풀와이드 사용 자체는 일본어/중국어 텍스트에서 매우 흔한 정상 패턴이라 오탐 위험이 큼). 대신 7단계(언어/구조 메타데이터)의 script 비율 계산에 원본 스크립트 정보를 넘겨 활용한다.

## 구현

- 표준 라이브러리 `unicodedata.normalize()`로 충분. 별도 서드파티 불필요.
- 선택적으로 `unicodedata2` (최신 Unicode 버전 테이블)를 설치하면 그걸 우선 사용 — Python 내장 `unicodedata`는 인터프리터 빌드 시점의 Unicode 버전에 고정되어 있어 최신 이모지/신규 문자에 대해 뒤처질 수 있음. (`11-dependencies.md` 참고)

| `ｶﾀｶﾅ` (반각 카나) | `カタカナ` | |
| `① ② ③` | `1 2 3` | 원문자 |
| `ﬁle` (ligature fi) | `file` | 합자 분해 |
